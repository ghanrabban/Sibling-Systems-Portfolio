# Portfolio requirements and traceability

Revision 3 · 13 October 2026 · Git version control and GitHub source publication added. **No requirement has an implementation pass result yet.**

This document translates the owner's goals into reviewable behavior. It applies SWEBOK Ch. 1 §§1–7, especially requirement quality (1-8), attributes and validation (1-14–1-16), and tracing/change impact (1-17–1-19). Page references and review scope are in [the reading record](./swebok-review-and-tailoring.md).

## Goals, stakeholders, and scope

| ID   | Confirmed owner goal                                      | Evidence of success to seek                                                                                                             |
| ---- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| UG01 | Publish projects and writing                              | Visitors find and read actual work; the owner can add and correct content using the documented workflow                                 |
| UG02 | Keep Navfolio's overall style and personalize its details | Owner accepts the paper/sage editorial presentation, typography, layout, and personal identity using real content                       |
| UG03 | Support English and Bahasa Indonesia                      | Both interfaces work; content is correctly labeled and paired only when a real translation exists                                       |
| UG04 | Execute the portfolio locally using Docker                | Documented Docker workflow supports editing, a clean release build and local deployment preview                                         |
| UG05 | Host the portfolio on Cloudflare Workers Free             | Static release fits the published free allowances and its actual deployment behavior is verified                                        |
| UG06 | Version the source with Git and publish it on GitHub      | Owner-accessible repository, meaningful change history, cloneable source, documented workflow and releases linked to deployed artifacts |

Candidate stakeholder perspectives for review: owner/editor, English reader, Indonesian reader, reader using a phone or assistive technology, and future maintainer. These perspectives are engineering analysis, not claims about measured audience demographics. The owner is the product/content decision-maker; the implementation role owns technical design, changes, and evidence. An additional reviewer is useful if available but is not assumed to exist.

Release scope proposed: Home, Writing, Projects, About, locale selection, light/dark mode, search, RSS, topic/archive navigation, and a static publishing workflow. Accounts, a database, contact-form backend, comments, newsletter, analytics, Media, Notes/Vibe, CMS, and automatic scheduled publishing are deferred. A later request for one of these becomes a scoped change with its own operating/security implications.

## Interpretation and priorities

UG01–UG03 are confirmed product preferences; UG04–UG06 are confirmed execution/source/hosting constraints. The detailed requirements below are **derived or proposed specifications**, open to refinement during the first implementation review. `D` means derived from a confirmed goal or a verified upstream constraint; `P` means an explicit engineering/product proposal. Neither implies the owner already accepted every precise threshold or mechanism. The [hosting assessment](./docker-cloudflare-hosting.md) records the platform evidence behind R20/R22; master-plan §11.1 defines the proposed Git/GitHub workflow.

P0 = essential foundation or correctness; P1 = required launch experience/quality in this proposal; P2 = deferred. All P0 and P1 items must pass or have an explicitly recorded scope change before the release candidate is accepted. Do not turn a failed requirement into a pass through relabeling. Implementation status: **planned for every row**.

Every future implementation change records its requirement/work-item IDs, relevant tests, and resulting commit/evidence reference. Traceability runs backward too: an added component with no requirement or maintenance rationale is a candidate for removal. Test counts do not replace reviewing the behavior that each requirement actually covers.

## Validation scenarios for the owner

1. Arrive on a phone, understand whose site this is, then open a real article and project.
2. Open an Indonesian page, follow its navigation, search for Indonesian writing, and subscribe to the Indonesian feed.
3. Switch a translated article in both directions; open an original-only article and understand the missing-translation message.
4. Explain your contribution from a project page and find the relevant public source/demo or an honest explanation of its availability.
5. Add and correct a publication using the authoring guide; understand what is private, what is only a preview, and what has actually been published.

These scenarios validate usefulness and understanding. Passing a generated-link test verifies implementation consistency, but cannot establish that the biography is accurate or the reading experience suits the owner.

## Change procedure

For a requested change, record: reason/source → affected requirement IDs → design/content/tests/hosting impact → revised effort and risk → decision and date → implementation/evidence. Small fixes that satisfy existing requirements need a concise work-item record, not a new approval ceremony. New features or altered scope require explicit acknowledgement of the tradeoff. Keep the current requirements set complete; use history to explain changes, not to force maintainers to reconstruct the specification from old messages.
