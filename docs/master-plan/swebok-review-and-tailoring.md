## Interpretation that governs this plan

The introduction explains that generally accepted knowledge is selected according to a project's needs (printed xl, PDF 41). Appendix B distinguishes a body of knowledge from normative standards and recommended practices (B-1–B-5, PDF 393–397). Therefore:

- Use SWEBOK to organize engineering reasoning and evidence. Do not advertise the portfolio as “SWEBOK certified,” “IEEE approved,” or formally conforming to a cited ISO/IEEE standard.
- Keep requirements, architecture, quality, security, and operations connected throughout incremental delivery. Chapter order is not a mandatory waterfall lifecycle.
- Scale the process to one owner and one implementation role. A few versioned documents and automated checks replace separate departments, formal review boards, and a large document suite.
- Treat thresholds, schedules, release gates, file structures, test IDs, and the chosen technology as **project decisions**, not values prescribed by SWEBOK.
- Verify current product documentation and any specific external standard before making a conformance claim. A citation inside SWEBOK does not by itself establish the applicable edition or every normative obligation.

## Deliberate tailoring

Use a **small, non-safety-critical, static publishing system** as the planning context. This is a project characterization, not an assigned formal integrity or maturity level. Publishing correctness, accessibility, owner workflow, maintainability, and supply-chain integrity deserve attention; domain-specific controls should follow actual risk.

| Practice                                     | Treatment and reason                                                                                                                                                                |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Requirements/architecture/test documentation | Keep compact and versioned together; link IDs rather than duplicate prose in separate templates                                                                                     |
| Quality assurance independence               | Separate construction, technical review, and owner acceptance activities; disclose that the implementation role may also test. Do not pretend there is an independent QA department |
| Formal methods                               | Use simple invariants, decision tables, and focused tests. No full formal proof, safety case, or model-checker procurement                                                          |
| Security                                     | Review dependencies, trusted MDX inputs, CI permissions, public output, and host configuration. No authentication framework or database controls unless those features are added    |
| Operations                                   | Retain rollback and backup rehearsal. No Kubernetes, multi-region failover, or 24/7 support promise for this scope                                                                  |
| Economics                                    | Use qualitative alternative comparison, effort ranges, and a recurring-cost register. No fabricated ROI, productivity history, or traffic forecasts                                 |
| Standards                                    | Consult relevant external specifications for precise criteria. No certification process or contractual conformance obligation is created by this plan                               |
| Measurement                                  | Track a handful of decision-useful measures. Avoid arbitrary line-count, commit-count, or universal code-coverage targets                                                           |
