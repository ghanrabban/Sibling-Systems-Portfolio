This combines several engineering responsibilities into one practical document. ## Responsibilities and working rules

The owner decides product purpose, public content, language voice, account/domain choices, spending and publication. The implementation role designs, builds, verifies, reports limitations, and prepares reviewable results. The owner becomes the ongoing operator unless another maintainer is explicitly assigned. Technical review and owner acceptance are distinct activities; neither is represented as independent certification.

Work is ready to implement when its purpose, affected requirements, dependency/owner, example inputs and expected behavior are understood. Low-impact presentation edits need an appropriate visual check, not an invented unit test for every style rule. Higher-risk shared rules—publication, translation, URLs, locale normalization—need explicit tests.

Work is done when the change satisfies its acceptance contract, relevant checks pass, evidence identifies the tested revision/environment, documentation remains accurate, and any residual limitation is recorded. A green build by itself does not establish content accuracy, accessibility, or product usefulness.

## Test design and execution record

Use specification-based tests for public behavior, focused unit tests for shared rules, integration tests for package/route/build boundaries, browser tests for interactions, and owner acceptance for purpose/voice. Start with the expected outcome; avoid snapshot suites that merely copy configuration. Use exploratory reading and navigation to complement planned cases.

Keep tests, fixtures and plans under version control. Each execution records test ID, requirement IDs, commit, build-date input, tool/browser versions, environment, fixture/content revision, steps, expected/actual outcome, result (`pass`, `fail`, `blocked`, `not run`, or `not applicable` with reason), and evidence/defect link. A tool timeout or missing browser is not a pass.

## Coverage, environments and quality targets

Use the production-generated site for system checks; development-server behavior is insufficient for search/indexing and generated metadata. Record exact versions at execution time. Proposed browser scope: current stable Chrome, Firefox, and Safari at execution; an actual mobile browser and VoiceOver/Safari on the available Mac. Identify unavailable environments early and record a substitution or limitation explicitly.

Viewport set: 320, 390, 768, 820, 920, 1024 and 1440 CSS pixels. Exercise Home, archive, article, project and About across representative combinations. Use full EN/ID/theme checks at 390 and 1440; targeted breakpoint and overflow checks at the intermediate widths. Add widths immediately around changed CSS breakpoints. This is risk-based sampling, not a claim to test every device combination.

For performance, use a recorded Chrome version, 390×844 emulated viewport, cold cache, 4× CPU slowdown, 1.6 Mbps download / 750 Kbps upload / 150 ms latency, one page at a time against a production-equivalent preview. Record the actual throttling tool/settings and machine. Measure local bundle sizes separately from hosted network behavior. Use light mode for the full run and check dark mode for additional loading/layout changes. Re-run only after meaningful performance changes or inconsistent results.

Accessibility reference: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) specifies, among other criteria, 4.5:1 contrast for ordinary text and 3:1 for large text, with defined exceptions; AA target sizing uses 24×24 CSS pixels or its stated exceptions. A complete applicability review is broader than those examples.

Field reference: [Web Vitals](https://web.dev/articles/vitals) uses LCP, CLS and INP, assessed at the 75th percentile with mobile/desktop segmentation. Its good thresholds are 2.5s, 0.1 and 200ms respectively. Field evidence may be unavailable for a new low-traffic site. Do not enable analytics automatically to obtain it or substitute lab medians for field percentiles.

## Focused threat model

Assets: unpublished content, accurate public identity, repository/build integrity, deploy/domain access and visitor privacy. Boundaries: owner edits → repository; external dependencies → build runner; build artifact → host; untrusted visitor input → browser search UI; outgoing links/requests → third parties.

Plan the following controls at B21:

- Treat MDX and dependency install/build scripts as executable trusted inputs. Do not accept arbitrary visitor MDX or execute unreviewed contribution code with deploy credentials.
- Pin supply inputs, inspect relevant advisories and record where Git-sourced packages are not covered by a registry scanner. A pin provides identity, not proof of safety.
- Keep deployment permissions minimal; separate untrusted preview/test execution from credentialed publication. Preserve owner control over accounts and domain access.
- Render search text and links safely; test harmless HTML-like text, unusual characters and disallowed link schemes. Review any use of raw HTML, SVG or executable embeds that ships.
- Exclude secrets and non-public source from `dist`; check copied assets and source-map policy. Explicitly decide repository and preview visibility. `robots.txt` and `noindex` guide indexing and do not enforce access control.
- Use Workers Static Assets' native `_headers` support for reviewed response headers and a content-security policy compatible with actual scripts. Verify HTTPS and hosted behavior; keep container/deploy credentials out of layers and public files. See the [hosting assessment](./docker-cloudflare-hosting.md) for platform sources and the upload boundary.

No security testing of the upstream public site is required for this plan. Verify controlled local/preview artifacts and owner-authorized infrastructure in implementation. If forms, authentication, analytics, comments or a CMS are introduced, revisit data collection, abuse cases, dependencies and operating costs.

## Configuration and change control

Control these items together: requirement/design documents, owner content and translations, assets/provenance, source and local overrides, upstream/fork SHAs, lockfile and registry selection, runtime/tool versions, build/index scripts, workflow/host configuration, tests/fixtures, release manifests and runbooks. Keep credentials outside the repository/artifact; record their purpose/owner and recovery procedure without recording values.

Use Git with a stable `main`, short feature branches and reviewed commits/PRs in the dedicated GitHub repository. Follow ADR10 and master-plan §11.1; associate annotated release tags with exact source commits and preserve published history. An issue/backlog entry and commit/PR are sufficient records for routine work. Do not impose a separate board for a one-owner project. Record material scope changes and package updates with impact on requirements, tests, estimated work and maintenance. Maintain a small debt list: item, reason, affected requirement/risk, consequence, owner, and trigger/date for reconsideration.

Proposed baselines: original analysis snapshot; verified source/tool baseline at G1; tested bilingual foundation at G2; real-content baseline at G3; identified release candidate at G4; deployed baseline at G5. A proposed baseline is not “approved” merely because this document names it.

## Release readiness and defect handling

G4 requires all required requirement checks complete, no unexplained failed/blocked checks, owner content validation, recorded Workers account/plan/origin/root base, an identified artifact within Free limits, and successful recovery rehearsal. A gap can prompt an explicit scope adjustment or release postponement; it must remain visible. Remote evidence is collected only within an authorized implementation/rehearsal scope.

Severity is separate from feature priority:

- S0: exposed secrets/unpublished sensitive material, corrupted release identity, or similarly urgent integrity incident. Contain immediately when discovered; block release.
- S1: a core journey, locale, accessibility requirement, publishing rule or deployment fails. Fix and re-test before release.
- S2: a limited defect with a working alternative. If it fails a launch requirement, fix or revise scope explicitly; otherwise record owner/rationale/follow-up.
- S3: cosmetic or optional improvement with no required behavior affected. May enter the deferred backlog.

Defect record: environment/revision, reproduction steps, expected/actual result, impact/severity, suspected cause clearly distinguished from proven cause, fix, regression check and outcome. Recurring failures receive a short root-cause review and preventive action. “Four covers failed” is an observation; an unverified network explanation is not a root cause.

## Release runbook to implement and rehearse

1. Freeze the candidate commit/content, production origin/root base, image/tool/package pins and publication-date input. Identify the clean Git release commit/tag and public GitHub source URL. Check the target Workers account/plan/name, domain access where needed, and saved known-good artifact/configuration where one exists.
2. Run required checks and the production build inside Docker, then generate Pagefind from eligible output. Enforce final upload file limits. Save logs, test status, dependency/image inventory, artifact checksum and limitations outside the public artifact.
3. Validate the artifact with local Wrangler using the deployment configuration, then perform any authorized remote rehearsal. Choose preview exposure deliberately; indexing controls do not protect private drafts. Inspect production-origin canonicals intentionally present in the candidate.
4. Perform T17/T19 content/author review and T18 recovery drill. Present the completed preview and readiness record when actual publication needs owner authorization. No public deployment is authorized by this planning task.
5. Supply deployment credentials only to the explicit pinned Wrangler upload step and deploy the reviewed static artifact without rebuilding content. Record account/name, version/deployment ID, time, configuration and artifact identity. No Docker image is uploaded as the website runtime.
6. Smoke-test root, both homes, a detail page per available locale, a project, search, feeds, assets, canonical origin/base and an unknown route. Do not report success until hosted behavior is verified.
7. On a material failure, redeploy the saved known-good artifact and matching configuration using the rehearsed procedure, verify it, record the incident, and fix forward in a new candidate. For a first launch with no prior version, prepare and rehearse a simple safe holding artifact. Do not assume a DNS edit is an instant rollback.
8. Publish concise GitHub release notes linked to the source tag and hosted release; record known limitations without exposing credentials. Hand over the release record, Git/Docker author guide, backup/recovery instructions, dependency/fork inventory, unresolved debt and maintenance ownership. Record completion and one improvement for the next release.

## Maintenance and service continuity

Proposed cadence below is a plan for the future operator, **not an automation or monitoring service created in this task**. Workers Free is the hosting constraint; no service-level or spending commitment beyond this plan is implied.

| When                                      | Activity and record                                                                                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every publication/change                  | Validate content, build, relevant regression tests and hosted smoke checks; retain release identity and prior good artifact                                                                       |
| First week after launch                   | Owner checks real reading/search/subscription flows and reports issues; prioritize escaped defects                                                                                                |
| Monthly                                   | Review dependency/base-image advisories, broken links, Docker build health, fork divergence, backups, Workers usage/plan notices, asset headroom and small debt items                             |
| Quarterly or after a host/pipeline change | Rehearse source restore and artifact rollback; review accessibility/performance after meaningful template changes; confirm operating costs/ownership                                              |
| Material vulnerability or service failure | Assess applicability and impact promptly; contain, recover, patch and test proportionately; record cause and follow-up                                                                            |
| Retirement or migration                   | Export source/content/assets and configurations; preserve important URLs with a documented redirect/archive policy where feasible; revoke obsolete credentials and cancel owner-approved services |

Classify maintenance as corrective (fix failure), preventive (remove latent fault), adaptive (framework/host change), additive (new capability), or perfective (improve performance/readability/documentation). Emergency work restores service first and receives follow-up review. These categories reflect SWEBOK 7-4–7-5 and make ongoing effort visible.

Back up committed source/content and retained original media outside the production host, with an owner-accessible copy separate from the working checkout. Preserve enough deployment configuration to rebuild. Retain at least the current and previous good release artifacts as a starting policy, subject to storage cost. Git alone does not back up untracked images, missing credentials or inaccessible accounts; the restore drill must expose those dependencies.

## Decision-useful measurements

| Goal                          | Question                                             | Measure and resulting decision                                                                                                                        |
| ----------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publish correct content       | Can unpublished or wrong-language material leak?     | T07/T06 failures and affected artifacts; any failure blocks release and prompts shared-rule review                                                    |
| Complete the promised scope   | Which requirements lack evidence?                    | Verified required IDs / required baseline IDs, plus explicit failed/not-run counts; resolve gaps instead of claiming percentage-complete from commits |
| Support useful reading        | Can representative readers complete core tasks?      | T17 task completion and observed obstacles; revise navigation/copy before optional features                                                           |
| Keep delivery economical      | Where is effort exceeding assumptions?               | Actual focused hours by phase, rework and new fork scope; re-estimate remaining work at G1/G2                                                         |
| Sustain the site              | Can the owner publish and recover?                   | T19 assistance needed, T18 restore time, build/dependency incidents; improve docs or simplify the architecture                                        |
| Avoid performance regressions | Did the changed assets/template make reading slower? | Same-profile LCP/CLS samples and transfer sizes; optimize the measured cause                                                                          |

Do not infer product maturity from the number of documents, a high Lighthouse score, raw test count, or a self-assigned maturity level. The evidence is the functioning site, dependable publishing workflow, known limitations, and ability to maintain it.
